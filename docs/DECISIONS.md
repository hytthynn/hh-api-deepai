# Архитектурные решения (ADR)

## ADR-001. Next.js как единый HTTP-слой

**Контекст.** Нужны UI, админ-API и три API-протокола на одном порту, локально.
**Решение.** Один Next.js 16 процесс: App Router для UI, Route Handlers для `/api/*` и `/v1/*`. `runtime = 'nodejs'`, `dynamic = 'force-dynamic'`.
**Альтернативы.** Отдельный Express/Fastify-шлюз (+1 процесс, +1 порт, дублирование конфига); serverless-разделение (неприменимо локально).
**Следствия.** Стриминг через `ReadableStream`; никакого edge-рантайма; gateway-код не импортирует React.

## ADR-002. Python-воркер для регистрации

**Контекст.** OAuth-контур отлажен в Python (`oauth.py`): 88% успеха на свежих логинах, известны все стадии отказа.
**Решение.** `engine/worker.py` — дочерний процесс с NDJSON-контрактом; Node управляет пулом, таймаутами и ретраями.
**Альтернативы.** Порт на TS (недели переотладки, детект Google от биндинга не зависит); in-process `pyodide` (не умеет Chrome).
**Следствия.** Два рантайма на машине; `npm run doctor` проверяет Python/playwright/Chrome; регистрация деградирует отдельно от шлюза.

## ADR-003. SQLite + Drizzle, без ORM-абстракций поверх домена

**Контекст.** Однопользовательское локальное приложение, единый писатель, нужны сложные выборки для статистики.
**Решение.** `better-sqlite3` (синхронный, WAL) + Drizzle для схемы и миграций. Репозитории возвращают доменные типы.
**Следствия.** Нет сетевой БД и пула соединений; синхронные вызовы допустимы в Route Handlers (запросы < 1 мс); миграции — файлы в `drizzle/`.

## ADR-004. Ключи хранятся хешем, секреты — AES-256-GCM

**Контекст.** Локальная машина, но cookies = полный доступ к аккаунтам, а ключи — к шлюзу.
**Решение.** HH-ключи: `sha256(pepper||key)`, показ один раз. BM-ключ, пароли, cookies: AES-256-GCM, ключ из `HH_SECRET` через scrypt.
**Следствия.** Потеря `HH_SECRET` = потеря секретов; предусмотрен экспорт списка аккаунтов без паролей.
**Обновлено.** Показ ключа больше не однократный: добавлен `key_enc` (ADR-021), проверка остаётся по хешу. RPM и отзыв пересмотрены в ADR-022.

## ADR-005. Один слот на аккаунт и failover только до первого байта

**Контекст.** Апстрим допускает одну coding-сессию на аккаунт (409 `session_busy`).
**Решение.** Слот в памяти процесса (lease 900 с), выбор по `last_used_at`, до 8 попыток. После первого SSE-чанка переключение запрещено.
**Следствия.** Пропускная способность = число активных аккаунтов; при 0 аккаунтов — 429 `no_account_available` с `Retry-After`.

## ADR-006. Три протокола через одну внутреннюю модель

**Контекст.** Клиенты говорят на Chat Completions, Responses или Anthropic Messages.
**Решение.** `normalize` → `ChatRequest` → апстрим → `render-*`. Никаких отдельных апстрим-вызовов на протокол.
**Следствия.** Один failover, один логгер, одна статистика; новый протокол = новый normalize + render, без изменений в транспорте.

## ADR-007. Джобы в процессе веба, защита через `locks`

**Контекст.** Отдельный worker-процесс усложняет запуск; Next dev перезапускает модули.
**Решение.** Runner стартует из `instrumentation.ts`, singleton в `globalThis`, признак владения — строка в `locks`. Второй инстанс видит баннер и не запускает cron/джобы.
**Альтернативы.** `npm run worker` (второй терминал), BullMQ/Redis (лишняя инфраструктура).
**Следствия.** Долгая джоба живёт в процессе веба; при рестарте помечается `failed: restart` и возобновляется вручную.

## ADR-008. Polling вместо WebSocket в UI

**Контекст.** Нужен прогресс джоб и живой хвост логов, нагрузка — 1 пользователь.
**Решение.** `setInterval` 1.5–2 с на `/api/jobs/:id` и `/api/logs`; без SSE в админке.
**Следствия.** Проще отладка, нет менеджера соединений; при 100+ строк логов — курсорная пагинация.

## ADR-009. Без лимитов закупки

**Контекст.** Владелец выбрал «без лимитов» (вопрос от 2026-11-14).
**Решение.** Продукт не блокирует трату; показывает оценку `quantity × price`, остаток кошелька до покупки и фактическую сумму после.
**Следствия.** Ответственность за количество — на пользователе; защита только техническая (одна джоба за раз, явное подтверждение в модалке).

## ADR-010. Cache Components не используем

**Контекст.** Next 16.4 рекомендует Cache Components, но все данные живые и персональные.
**Решение.** Отключено; `force-dynamic` на всех страницах и роутах.
**Следствия.** Нет риска закешировать баланс или ключи; TTFB локально остаётся в бюджете 120 мс.

## ADR-011. Импорт легаси BM-ключа из `.env`

**Контекст.** До hh-api владелец держал ключ BM в `.env` (и в старом `bank.jsonl`-контуре); UI настроек должен быть единственным источником истины, а ключ — лежать только в зашифрованном `settings`.
**Решение.** `runtime.boot()` однократно читает `BM_KEY` (или `HH_BM_KEY`) из окружения. Если `settings.bm.api_key` пуст — ключ шифруется `AES-256-GCM` и записывается в `settings`, после чего переменные удаляются из `process.env`. Если настройка уже есть — переменная игнорируется, причина попадает в `buildWarnings` и видна в `/api/overview → runtime.warnings`.
**Альтернативы.** Оставить ключ в `.env` навсегда (два источника истины, маскирование в UI врёт); удалить `.env`-ключ вручную (потеря при первом запуске).
**Следствия.** Ключ в `.env.local` перестаёт действовать после первого успешного старта; ротация — только через Настройки. Секрет никогда не попадает в логи (`redact.ts`) и в ответы (`maskSecret` → `sk_live_…ab12`).

## ADR-012. Служебные admin-эндпоинты сверх §10

**Контекст.** SPEC §10 перечисляет обязательные роуты, но экраны §21 (индикатор движка, экспорт аккаунтов, очистка логов, список джоб, read-only ретеншен) требуют данных, для которых нет отдельного контракта.
**Решение.** Добавлены четыре эндпоинта и два поля, не меняющих семантику существующих:
`GET /api/engine` (health движка + текущие `engine.*`, кеш 60 с, `?refresh=1`), `GET /api/accounts/export` (CSV без cookies/паролей — только `email,status,balance,...`), `DELETE /api/logs` (очистка таблицы `logs`), `GET /api/jobs` (последние джобы для баннера и модалки), `runtime` в `GET /api/overview` (`warnings`, `locked`, `started_at`, `models_sync_due`) и `retention` в `GET /api/settings` (значения из env, read-only).
**Альтернативы.** Расширять `/api/overview` всем (перегруженный ответ, лишние запросы к BM); не показывать статус движка (нельзя отличить «нет Chrome» от «упал Python»).
**Следствия.** Эндпоинты под тем же `api()`-guard (сессия + same-origin на мутациях); `DELETE /api/logs` не трогает `requests`. При росте UI их набор фиксируется здесь, а не в SPEC.

## ADR-013. CSP nonce в `proxy.ts`, а не `middleware.ts`

**Контекст.** SPEC §22.7 требует `default-src 'self'`; без nonce гидратационные inline-скрипты Next блокируются. Next 16.4.6 объявил файловую конвенцию `middleware` устаревшей и печатает предупреждение на каждом старте.
**Решение.** Nonce выдаётся в `proxy.ts` (`export function proxy`) — тот же matcher, что был у middleware: всё, кроме `/api`, `/_next/static`, `/_next/image`, `favicon.ico` и prefetch-запросов. Nonce кладётся в request-заголовки (`x-nonce` + `content-security-policy`) и в response-заголовок; Next проставляет его в `<script nonce>`.
**Альтернативы.** Оставить `middleware.ts` (вечное предупреждение сборки); `'unsafe-inline'` (ослабление CSP, запрещено §22.7).
**Следствия.** Предупреждение исчезло; CSP проверяется в smoke-тесте (`content-security-policy: default-src 'self'` в ответе `/login`).

## ADR-014. Глобальные горячие клавиши навигации

**Контекст.** §21 просит быструю навигацию по разделам без мыши; при этом ввод в поля и модалки не должен перехватываться.
**Решение.** Префиксная схема `g` + клавиша: `g o` — Обзор, `g a` — Аккаунты, `g k` — Ключи, `g m` — Модели, `g l` — Логи, `g s` — Настройки; `/` — фокус в поиск текущего экрана, `Esc` — закрыть модалку/снять фокус. Обработчик игнорирует события при `event.target` внутри `input/textarea/select/[contenteditable]` и при открытом модальном окне (кроме `Esc`). После слияния статистики с обзором (ADR-022) освободившаяся клавиша `s` закреплена за «Настройками», `g t` больше не используется.
**Альтернативы.** `Ctrl+1…7` (конфликт с вкладками браузера); отдельный command palette (лишняя фича сверх §2.1).
**Следствия.** Одна реализация в `src/ui/shortcuts.ts`, без библиотек; подсказка в футере сайдбара.

## ADR-015. Интеграционные тесты через HTTP-мост к тем же хендлерам

**Контекст.** §25.2 требует 12 сценариев «на реальном HTTP», включая стриминг, обрыв клиента и конкурентность. Поднимать `next dev` в тестах — 30+ секунд на файл и нестабильно.
**Решение.** `tests/fixtures/gateway.ts` поднимает `node:http`-сервер на 3211 и передаёт запросы в экспортированные хендлеры (`handleChat`, `handleResponses`, `handleAnthropicMessages`, …), конвертируя `IncomingMessage` → `Request` и `Response.body` → `ServerResponse` (с `reader.cancel()` при отключении клиента). Upstream-мок на 3212 подменяет `API_BASE` через `vi.mock('@/src/adapters/upstream/headers')`; продуктовый код не содержит тестовых веток.
**Альтернативы.** `next start` + сборка (медленно); тестировать только чистые функции (не покрывает слоты, failover и SSE).
**Следствия.** 12 сценариев идут ~7 с вместе с юнит-тестами; проверяются реальные заголовки (`x-hh-attempts`, `x-request-id`), коды и порядок SSE-событий.

## ADR-016. Объектная форма `tool_choice` в Anthropic-нормализаторе

**Контекст.** Anthropic при `tools` присылает `tool_choice: {"type":"tool","name":"get_time"}` (и `{"type":"any"}`), а внутренняя модель запроса — OpenAI-форма.
**Решение.** `normalizeAnthropic` принимает обе формы: строка (`auto|any|none`) маппится в `auto|required|none`, объект `{type:'tool',name}` → `{type:'function',function:{name}}`, `{type:'auto'|'any'|'none'}` → строка. Неизвестное значение — 400 `tool_choice: invalid value`.
**Альтернативы.** Отклонять объектную форму (ломает Claude Code при первом же tool-use); хранить Anthropic-форму до рендера (усложняет failover-нормализацию).
**Следствия.** `tool_choice` доезжает до апстрима без потерь; покрыто `tests/unit/normalize.test.ts` (B-016).

## ADR-017. Общее мутабельное состояние — на `globalThis`

**Контекст.** Next 16 исполняет `instrumentation`, route handlers и RSC в одном процессе, но каждый в своём module graph: модульный singleton существует в нескольких экземплярах. Из-за этого второй граф заново «бутился», проигрывал гонку за `locks` и отдавал 503 `db_locked` с собственным pid, а лог-записи копились в невидимом буфере (B-014).
**Решение.** `src/lib/global-state.ts` — `globalState(key, init)` поверх `globalThis.__hhState` (тот же приём, что у соединения SQLite). На нём живут: runtime bundle (`booted`, `lock`, `signalsBound`, `state`), лог-синк (`sink`, `minLevel`, `pending`), токен-бакеты RPM, слоты аккаунтов, `EnginePool`, кеш кошелька BM, счётчики попыток входа.
**Альтернативы.** `globalThis`-переменные вручную в каждом модуле (дублирование и разные имена); отказ от `instrumentation` и ленивый boot только из роутов (тогда `npm start` не поднимает cron до первого запроса).
**Следствия.** Ровно один boot на процесс; `acquireLock` дополнительно забирает лок у своего pid, у мёртвого pid и у протухшей строки (`tests/unit/locks.test.ts`). Тесты используют `:memory:` БД и `resetGlobalState()` в setup.

## ADR-018. Preflight provision и прерываемая отмена регистрации

**Контекст.** Проверочный запуск provision был принят при `chrome_ok:false`: заказ BM успел купить логин, а cancel оставил job `running`, пока Playwright ждал OAuth. Runner и cancel-route также имели разные module-local карты в Next route graphs.
**Решение.** Проверять `engineHealth().chrome_ok` перед созданием и запуском покупки; отмену сначала атомарно фиксировать в `jobs.status`, затем abort-ить in-flight `EngineWorker` через process-wide `globalState()` — worker убивает дерево процессов, включая Chrome. Прерванный item возвращается в `purchased`, чтобы его можно было дорегистрировать через `resumeJobId`.
**Альтернативы.** Ждать таймаут Python (OAuth продолжает выполняться, job висит); помечать купленный логин `failed` (теряется resumability).
**Следствия.** Нет покупки при недоступном Chrome; отмена сразу видна в API и останавливает браузер. `EnginePort.register` принимает `AbortSignal`.

## ADR-019. Приёмочная проверка аккаунтов — job `probe`, а не `probe.py --all`

**Контекст.** §25.3 требовал сверять баланс аккаунтов с `probe.py --all`, но этот CLI читает легаси `bank.jsonl`, которого в текущей архитектуре нет (`HH_ENGINE_NO_BANK=1`, источник истины — SQLite). Формально пункт приёмки был невыполним.
**Решение.** Приёмочная проверка баланса и живого чата идёт через `POST /api/accounts/check-all` → job `probe` (тот же путь, что у cron раз в 5 минут): theos + короткий чат на free-модели, результат в `job_items` и `accounts`. `probe.py` остаётся ручной диагностикой легаси-банка и вебом не используется.
**Альтернативы.** Дамп БД в `bank.jsonl` перед приёмкой (лишний код и риск утечки cookies); удалить пункт из §25.3 (теряется требование).
**Следствия.** §25.3 ссылается на `check-all`; результаты видны в UI и `jobs`, а не только в консоли Python.

## ADR-020. Легаси-контур удалён из репозитория

**Контекст.** До hh-api существовал отдельный контур: HTTP-шим `legacy/shim.py` (порт 8770), читавший `bank.jsonl`, CLI `engine/wave.py`/`redeem.py`/`probe.py`, плюс `accounts.txt` и `bank.example.jsonl`. После переезда на SQLite (`HH_ENGINE_NO_BANK=1`, ADR-019) ни один файл в `app/`, `src/`, `scripts/`, `tests/` на этот контур не ссылался: шим не запущен, `bank.jsonl` не читается и не пишется, импорт в БД отсутствует. При этом `bank.jsonl` и `accounts.txt` хранили пароли и cookies в открытом виде.
**Решение.** Удалены `legacy/`, `bank.jsonl`, `accounts.txt`, `bank.example.jsonl`, `engine/{wave,redeem,probe}.py`, `__pycache__`, `shim*.log`, `tsconfig.tsbuildinfo`. Из `.gitignore` убраны правила мёртвых файлов (`bank.jsonl`, `accounts.txt`, `.shim.pid`, `tmp_*.json`, `*.out`, `.wave.lock`), из `eslint.config.mjs` — игнор `legacy/**`, из README/SPEC — упоминания каталога. Остались только `engine/{worker,oauth,dpcode}.py` + `requirements.txt`.
**Альтернативы.** Оставить каталог «справочно» (лишние секреты на диске и ложное впечатление, что шим поддерживается); оставить `bank.example.jsonl` как формат (формат нигде не парсится).
**Следствия.** Единственные источники истины — `data/hh.db` и `prof/`; `HH_ENGINE_NO_BANK=1` остаётся страховкой в `engine/dpcode.py`. Удаление обратимо через историю git (`git show 978e9a4:legacy/shim.py`).

## ADR-021. Показ полного ключа из UI (`key_enc`)

**Контекст.** §11 требовал показывать `hh-api-…` единственный раз при создании: в БД лежал только `sha256(pepper || key)`, восстановить ключ было нельзя. Владелец терял ключ после закрытия модалки, и единственным выходом было создание нового ключа и перенастройка клиентов.
**Решение.** В `api_keys` добавлена колонка `key_enc text` — полный ключ в AES-256-GCM (`v1.<iv>.<tag>.<ct>`, тот же мастер-ключ из `HH_SECRET`). При создании пишутся и хеш, и шифртекст. `GET /api/keys/:id` возвращает `{key,record}`, расшифровывая `key_enc` на сервере; UI показывает значение в модалке по кнопке «Показать». Для ключей, созданных до миграции (`key_enc IS NULL`), ответ — 409 `key_not_revealable`.
**Альтернативы.** Хранить ключ в открытом виде (утечка БД = утечка всех ключей); детерминированная генерация из id/секрета (предсказуемость); оставить «один раз» и добавить ротацию (лишний сценарий вне §2.1).
**Следствия.** БД содержит и хеш, и обратимый шифртекст: компрометация `HH_SECRET` вместе с файлом БД раскрывает все ключи. Смена `HH_SECRET` делает `key_enc` нечитаемым (как и `password_enc`/`cookies_enc`), ключи при этом продолжают работать — проверка идёт по `key_hash` с новым перцем, поэтому при смене секрета все ключи перестают аутентифицироваться и перевыпускаются. Список `/api/keys` по-прежнему отдаёт только `prefix`/`last4`; полный ключ не попадает в логи (`redact`).

## ADR-022. Суммарная квота токенов, глобальный RPM и физическое удаление ключей

**Контекст.** RPM задавался на ключ (`api_keys.rpm_limit`), лимита токенов не было, «отзыв» помечал строку `revoked_at` и оставлял её в БД навсегда. Владелец попросил: лимит запросов — один на шлюз в «Настройках», у ключа — необязательная суммарная квота токенов без выбора периода, удаление — окончательное.
**Решение.** Колонки `api_keys.rpm_limit` и `api_keys.revoked_at` удалены (миграция `0001_keys_plaintext_quota`), добавлена `token_limit integer NULL` (NULL = без лимита, значение — суммарно за всё время жизни ключа). RPM хранится в `settings['gateway.rpm_limit']` (по умолчанию `'60'`, диапазон 1–6000), читается через `getInt` каждый запрос с фолбэком на `env.defaultRpm`; token bucket общий на процесс (`src/lib/rate-limit.ts`). В `pipeline.begin()` порядок проверок: аутентификация → `tokensUsedByKey(id) >= token_limit` → 429 `token_quota_exceeded` → RPM bucket → 429 `rate_limit_exceeded`. `DELETE /api/keys/:id` выполняет `deleteKey()` (физический `DELETE`), `findActiveKeyByHash` заменён на `findKeyByHash` без фильтра по `revoked_at`.
**Альтернативы.** Оставить `revoked_at` и скрывать отозванные из списка (мусор в БД, путаница в метриках); период квоты (`day`/`month`) — владелец явно исключил выбор периода; RPM на ключ плюс глобальный (две ручки вместо одной).
**Следствия.** `requests.api_key_id` — `ON DELETE SET NULL`, поэтому логи удалённого ключа остаются с `key_name = NULL` (UI показывает `#id`). Счётчик `tokensUsedByKey` — `SUM(input_tokens + output_tokens)` по `requests` с индексом `idx_requests_key`; стоимость запроса не учитывается, поэтому квота проверяется до запроса и может быть превышена на один запрос. Удаление необратимо: восстановить ключ можно только созданием нового. Миграция `0001` перед удалением колонки выполняет `DELETE FROM api_keys WHERE revoked_at IS NOT NULL` — иначе ранее отозванные ключи стали бы валидными (фильтр по `revoked_at` исчез). В dev-БД это удаление выполнено отдельно по бэкапу (`id 4–20, 22–24`), потому что миграция применилась до правки файла; два оставшихся ключа созданы до ADR-021 и не показываются (409 `key_not_revealable`).

## ADR-023. Импортированный аккаунт сразу проходит вход

**Контекст.** `POST /api/accounts/import` сохранял `email/password` как `pending` без cookies. Такой аккаунт был виден в UI, но не мог участвовать в gateway pool, и отдельного способа «дологиниться» не было.
**Решение.** Импорт сначала проверяет Python-воркер и Chrome, затем создаёт `pending` аккаунты с `password_enc` и ставит job `login` (`params={accountIds[]}`) без закупки BM. Job использует общий с `provision` код `src/jobs/auth.ts` (`authenticateItem`): browser login, шифрование cookies, probe и переход в `active`; UI показывает прогресс в том же окне импорта. Ответ импорта расширен полем `jobId` (`null`, если новых аккаунтов нет). Пока активен другой `login`-job, импорт отвечает 409 `job_running`, чтобы не запускать два входа параллельно.
**Альтернативы.** Логинить синхронно внутри HTTP-запроса (долгий запрос, нет прогресса и отмены); отдельная реализация входа (дублирование retry, шифрования cookies, probe и стадий).
**Следствия.** Логины и пароли не попадают в `jobs.params`, там только id аккаунтов; пароль читается из `password_enc`. Ошибка одного входа видна в `job_items` (`account_not_found`, `no_password`, стадия регистрации/пробы), job завершается `done` при частичных ошибках, как `provision`. `spent_usd=0`. Покрыто `tests/integration/login-job.test.ts`: вход каждого аккаунта, cookies/machine/probe, дедупликация импорта и preflight без Chrome.
